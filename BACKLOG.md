- [x] **LLM features: built 2026-10-13 (code done, not seen in Obsidian; see "Not yet tested").** The plugin calls no LLM, has no LLM key and no new host, and sends nothing; each feature is a command that puts a prompt on the clipboard (with a preview of exactly what will be copied), and the user pastes the LLM's answer back where the plugin can read it. **Every prompt states the exact JSON the LLM must answer in** (field names, allowed values, one example), so the answer can be validated before anything changes. Three prompt features (the first is the existing item **Search review with an LLM**, below):
  1. **Review from results:** feed definition + the ledger report (rates by tier, topic, month, rule version; candidate terms) + the decisions data set (earlier suggestions with approved or denied and why) -> suggestions to add, remove or move terms, change a topic, change a group's role. Answer JSON: a list of suggestions, each with a kind, the target (topic number, group name, drop or lower list), the new value, and a reason. Pasting the answer opens **Review suggestions**: Accept or Reject each, accepted ones edit the feed, every verdict is stored in the decisions file so the next prompt tells the LLM what was refused and why.
  2. **Search-term review and tweak (new, owner):** a prompt for improving the OpenAlex query strings themselves (the feed's `topics`), from the current topics, what each returned and had dropped in the scan log, and a short note from the owner about what they are after. Answer JSON: for each topic keep / change / add / remove with the new query string and a reason. The pasted queries are checked before use (balanced brackets and quotes, as the feed editor does) and can be tried with the existing **Test** button, which shows tier counts and cost, before the feed is changed.
  3. **New feed from a description and example papers (new, owner; clarified 2026-10-13: the examples are PDFs or web pages the user gives to the LLM directly, in the chat):** the command's window asks for two things only: a description of what the user wants to follow, in their own words, and **how many example papers** they will attach (the number). The plugin builds a prompt that says "N example papers (PDFs or links) are attached to this chat: read them, and build the feed from what they have in common" and asks for a complete importable feed JSON, the same format as `docs/feeds/*.json` and the **Import feed** box (name, topics, concept groups with roles, drop and lower terms, years from; Zotero collection and project left empty), written so that the attached papers would be found and ranked high. The prompt asks the LLM to say, in an extra `notes` field the importer ignores, which attached papers its terms would still miss and why. The plugin never sees, reads or sends the papers, so there is nothing to look up or upload; the user attaches them in the LLM's own chat window. The answer is pasted into the existing import, which already validates it, and the **Test** button then shows what the search would return. An LLM that cannot open an attachment or link must say so instead of guessing (the prompt says this).
  Shared: one place to build prompts (a pure module with the JSON schemas, tested against the real validators so a schema cannot drift from what the importer accepts), the prompts say what the plugin's tiers and groups mean (required, boost, priority; drop and lower), a privacy note that titles go wherever the user pastes them, and optional inclusion of titles. Other ideas still on the table, none needed for this: a one-line `takeaway::` suggestion from an abstract (never filled automatically); suggesting a project collection for a paper; "why was this paper ranked or dropped" (needs no LLM: the matched terms are known). No new host: OpenAlex and Zotero only; the Zotero index is read-only and stays on the device.
